# 晴阅 1.12 旧模块交付复审（只读）

审查对象：当前主线 `QingYuePDF`（1.11）对照四个从 `579315d` 旧基线开发的 worktree。初始阶段只读审查旧实现；随后选择性整合全库搜索并完成当前主线测试，实际交付范围见 1.12.0-review.md。旧交付中的“编译通过”只能证明其当时的组合，不能证明当前主线的运行、恢复和升级安全。

## 结论与优先级

| 优先级 | 模块 | 判断 |
| --- | --- | --- |
| P0 | 多页笔记 | 有 1.12 核心价值，按 notes 文件集选择性移植并重做备份事务接线；不能整分支覆盖。 |
| P1 | 全库搜索 | 搜索引擎/索引缓存可独立复用；OCR 与主线同名实现冲突，须整合为现有 OCR 的文本提供方。 |
| P1 | 学习与复习 | `ReviewScheduler`、`SplitGeometry` 等纯逻辑可以先合；完整学习台依赖多页 notes 和备份目录合并，须在其后。 |
| P2 | WebDAV | 传输与状态机可复用；下载恢复必须待统一备份数据边界、学习合并和设备验证完成后开放。 |

## 多页笔记（`fd7e`, `6f08e86`）

- 可复用源码：`QingYuePDF/app/src/main/java/cn/qingyue/pdf/NoteDocument.java` 的 v1→v2 读取、`pageCount/currentPageId/pageText`；`NoteStore.java` 的 `contentRevision/acquireSnapshot/isSnapshotCurrent` 与保存世代；`NoteCanvasView.java`、`NoteActivity.java`、`NotePageDialog.java` 的编辑 UI；`NoteExport.java`、`NoteExportProvider.java` 的可移植 `.qynote` 与 PDF/PNG 导出。接口明细见 `fd7e/笔记app/delivery/notes-api.md`。
- 接线：主线 `BackupManager.java:143-150, 203-238, 294-354` 目前直接收集 `notes/<id>` 文件并在 `NoteStore.class` 锁内生成快照；移植后应以 `ConsistentSnapshot` 取得正文与被租住的图片，且不在全局锁内做归档 I/O。主线 `MainActivity.java` 的笔记跳转要传 0-based `page` / 稳定 `notePageId`；`AndroidManifest.xml` 注册只读 `.NoteExportProvider`；用户可见导入入口调用 `NoteExport.restoreArchive`。动态纸色由 `AppColors.PAPER` 接通。
- 阻断：当前 `NoteDocument.java` 已是 **VERSION=2 的单页文本格式**，而 `fd7e` 也标为 VERSION=2，却在读入版本号后先读取两个 long 和 active/pageCount；当前主线接下来读取 UTF template。两种 v2 字节布局直接冲突，不能按旧交付所述的 v1→v2 路径整文件覆盖；必须设计新版本号与双 v2 迁移读取器，并用现有真实笔记验证。现有 `NoteStore.java` 是不同的待写/删除实现，整文件替换必须验证主线 `BackupManager`、`NoteSourceActions` 的调用和删除事务。

## 全库搜索与 OCR（`c914`, `a336f62`）

- 可复用源码：`GlobalSearchEngine.java`、`GlobalSearchSource.java`、`GlobalSearchLibrarySource.java`、`GlobalSearchPdfSource.java`、`GlobalSearchActivity.java` 及 provider 接口；搜索缓存为可重建 `files/search/global-search-v1.bin`。笔记来源由 `RecognitionNoteTextProvider.java` 对接 notes 的 `pageText/contentRevision`。其 `OcrTextIndex/OcrTextStore/OcrSaveQueue` 可参考更正文本的持久化和恢复重映射。
- 接线：主线 `MainActivity.java:449` 已有 `onNewIntent`，搜索结果走现有内部跳转并重新核验索引；Manifest 添加 `.GlobalSearchActivity`。主线现有 `OcrActivity.java` 已继承 `ThemedActivity` 并能生成 hOCR、可搜索 PDF；保留其 UI/识别导出路径。本轮搜索新增 `RecognitionNoteTextProvider`、`RecognitionOcrSidecarProvider`、`RecognitionReaderTextProvider`，分别读取当前单页 TEXT、v1/v2 OCR 侧车和 ReaderStore.TextBox。OCR 搜索使用 `OcrSidecar.loadForPdf(identityHash, actualPdfHash, false)`，旧 v1 转换件若无实际 PDF hash 不进入索引。主线 `BackupManager.java:160-168` 备份的是每个文档的 `recognition/<id>`，旧交付的 `recognition/user/ocr-text-v1.bin` 不是同一格式，不予移入。
- 阻断：旧分支同名 `OcrActivity/OcrEngine/OcrImageLoader/OcrModelInstaller/OcrCancellation` 会覆盖主线功能，不能直接合；旧分支 `app/build.gradle`、`build-apk.ps1`、OCR AAR/模型/许可需与主线依赖清单逐项核对。旧 OCR 的 16 KiB 静态检查、测试签名 APK 不等于设备运行；搜索结果不能呈现已失效 PDF/OCR 正文。

## 学习双栏、录音、复习（`bb89`, `3dde70c`）

- 易先合的小模块：`ReviewScheduler.java`（无 Activity 的间隔计算）、`SplitGeometry.java`（分栏比例）、`StudyPageSelection.java`；各自 JVM 测试可带入。这些不应触碰主线数据格式。
- 完整模块可复用 `LearningActivity.java`、`SplitPaneLayout.java`、`StudySourceStore.java`、`ReviewStore.java`、`AudioSessionController.java`、`AudioNoteBridge.java`、`LearningBackupMerger.java`。Manifest 注册 `.LearningActivity` 和按需录音的 `RECORD_AUDIO`；主线 `MainActivity` 提供 `docId/noteId/page/notePageId` 入口并验证来源未回收。Activity 需继承主线 `ThemedActivity`。
- 阻断：`LearningActivity.java:209-215, 352, 465` 直接调用当前 notes 所无的 `currentPageId` 与扩展 Host，必须在解决双 v2 笔记格式后接。主线 `BackupManager` 遇学习 canonical 路径冲突目前会抛错并 fail closed，**不会**成功后藏到 `restored-<tx>`；旧交付对此的描述不适用于当前主线。若要 KEEP_BOTH，仍需 `LearningBackupMerger.prepare` 在 staging 合并，事务性替换 `files/learning` 并在失败时回滚；仅安装 `LearningBackupRemapper` 不够。需阻止目录交换期间的学习写入，并用真实 `.qyb` 连续 KEEP_BOTH 恢复两次验证录音和附图引用。PDF 侧仍是浏览模式，不具选区截图 API。

## WebDAV 手动快照（`be27`, `879b2a4`）

- 可复用独立类：`SyncEngine.java`、`WebDavHttpTransport.java`、`WebDavTransport.java`、`SyncEndpoint.java`、`RemoteSnapshotDescriptor.java`、`CredentialStore.java`；`SyncBackupArchiveSource.java` 调用主线 `BackupManager.createSnapshot/validate/restore(KEEP_BOTH)`。上传回读校验与条件 ETag 更新值得保留。
- 接线：Manifest 加 `INTERNET`、`usesCleartextTraffic=false`、`.SyncActivity`；主窗口新增手动入口。同步必须使用最终统一的 `.qyb` 内容，包括多页 notes 一致快照、OCR 唯一存储格式及 `files/learning` 事务合并。`SyncBackupArchiveSource.java:11-20` 当前默认只装 `LearningBackupRemapper`，须改用最终恢复流程。
- 阻断：交付文档所述 `restoreValidated` 最终索引写入风险在主线 `BackupManager.java:538` 已由 `LibraryStore.saveIfRevision` 修复，无需重做此点；学习 canonical 目录缺口仍在。远端快照指针设计需要真实 WebDAV/Android Keystore/TLS/恢复中断测试；在这些验证完成前不开放下载恢复。没有历史列表/远端清理，首次发布 UI 应明确只操作最新快照。

## 建议整合顺序与闸门

1. 本轮实际合入全库搜索核心：使用当前 LibraryStore v2、单页 NoteDocument.TEXT 与 OcrSidecar；保留现有 OCR 识别/导出。`GlobalSearchActivity` 的公开启动方式是 `startActivity(new Intent(this, GlobalSearchActivity.class))`；需主控注册 Manifest 和加入口。内建 provider 由 Activity 自己安装，无须 QingYueApplication。
2. 设计新的笔记版本号，兼容区分已发布单页 v2 和旧分支多页 v2，再改 `BackupManager` 快照接口、Provider/导入入口；用 v1 笔记、图片、待写内容和完整 `.qyb` 验证。
3. 接学习 UI、录音桥和完整目录合并；跑两次真实归档 KEEP_BOTH 及失败回滚。
4. 接手动 WebDAV；上传、下载与恢复的真实设备/服务端测试通过后开放恢复按钮。

以上路径均相对各 worktree 或主线 `QingYuePDF`；应 cherry-pick 选定文件/逻辑并针对当前主线解决冲突，不机械合并整分支。
